# ADR 0001: MCP 0.2, six tools on endpoints the engine already has

Date: 23 Oct 2026 (run-1023, build #8 of the competitor parity check)

## Problem
`@straitlink/mcp` 0.1.0 has 10 tools. People who work from an AI assistant still have to open the dashboard
to answer "how much of my plan have I used?", "why did my webhook stop?", "send that failed event again",
"is my webhook endpoint up?", "which referral codes convert?" and "turn this link off". Linkrunner's
connector has 44 tools (their count, from an unauthenticated `tools/list` on 23 Oct), including
`get_billing_usage`, `test_webhook` and `get_postback_delivery_log`.

## Who it serves
A developer or marketer with Strait in Claude Code / Cursor / Claude Desktop, using their own secret key.

## Options
1. **Do nothing.** The dashboard covers all six. Cost: agent users leave the assistant for routine checks.
2. **Hosted OAuth MCP with sign-up inside Claude** (Linkrunner's headline). L-sized: authorisation
   server, consent screen, token storage, cso review. Later (PARITY section 5).
3. **Extend what exists (chosen).** Six thin tools in `src/tools.ts`, each one HTTP call to a public,
   documented engine endpoint (OpenAPI operationIds below), with the same client, error and
   annotation patterns as 0.1.0. No new engine endpoint, no new dependency, no DB change.

| Tool | Endpoint (operationId) | Kind | Confirm |
|---|---|---|---|
| `get_usage` | GET /v1/usage (getUsage) | read | no |
| `get_referrals` | GET /v1/referrals (getReferrals, preview) | read | no |
| `list_webhook_deliveries` | GET /v1/webhooks/{id}/deliveries (listWebhookDeliveries); without an id, GET /v1/export?part=webhooks (exportData) to list the webhooks | read | no |
| `test_webhook` | POST /v1/webhooks/{id}/test (testWebhook) | write (sends one `ping`, not stored, not retried) | no |
| `redeliver_webhook_delivery` | POST /v1/webhook-deliveries/{id}/redeliver (redeliverWebhookDelivery) | write (re-sends a real event to the customer's system) | **yes** |
| `deactivate_link` | DELETE /v1/links/{slug} (deactivateLink) | destructive (taps get the "link not found" page until it is turned back on, 0.2.1 below) | **yes** |

Confirm rule: a tool that changes what live taps do, or re-sends a real event into the customer's
systems, previews first and acts only with `confirm: true` (the `update_link` pattern). `test_webhook`
sends only a `ping` the receiver can ignore, so it acts at once; the name and description say so.

Webhook ids: the API has no "list webhooks" operation, but the export already returns the webhook
configuration (no signing secrets). `list_webhook_deliveries` without `webhookId` returns that list,
reduced to id, receiver site (last two host labels, e.g. `zapier.com`), events and active: the full URL
is dropped because receiver URLs are often capability URLs (Zapier, Slack; Pipedream and ngrok put the
secret in the subdomain) and don't need to enter a model's context.

Referrals: `/v1/referrals` is a preview and answers 404 until the engine runs with `REFERRALS=on`
(prod answered 404 on 23 Oct). The tool turns that 404 (only the engine's `{"error":"not found"}` body) into a
plain "not switched on yet" result.

## Security lens (STRIDE)
- **Spoofing / key exposure.** The key stays in `STRAIT_SECRET_KEY`, is sent only as a Bearer header to
  the configured engine, never in a URL. Tool output and error text go through one redaction step that
  replaces anything shaped like a secret key (`st_live_…` / `st_test_…` as its own token, which covers every
  key `isSecretKey` accepts) with `st_…[redacted]`.
  Nothing is written to stdout/stderr per call.
- **Tampering / path injection.** Ids are validated as UUIDs and slugs by the existing regex before any
  call, and every path segment is `encodeURIComponent`-ed.
- **Data exposure.** Deliveries never carry payloads (engine); the webhook list drops URLs to their site;
  `test_webhook` returns status and timing only (engine SEC-15).
- **Abuse / DoS.** The engine's own limits apply (usage and referrals 30/min, delivery lease 2 min).
  The tools add no loops.
- **Least privilege.** Every tool calls the one endpoint made for its job with the key the user already
  gave this server; no tool needs the admin key, a session or a wider scope. The engine enforces the
  workspace boundary (a webhook or delivery id from another workspace is a 404).

## Architecture lens
Coupling: one more consumer of six public, versioned operations; if the engine renames a field the
tool still returns the engine's JSON as is (no reshaping except the webhook list). Failure modes:
engine 4xx/5xx become tool errors with the engine's message (existing `runTool`). Scale: one HTTP call
per tool call.

## Cost
None (npm publish under the existing token).

## 0.2.1 addendum (23 Oct 2026): paused links from Claude

Engine ADR 0041 (live 300e5c6) added `GET /v1/links?status=paused` and `PATCH /v1/links/{slug}`
with `{ "isActive": true | false }` sent alone. Extend what exists instead of a new tool:
- `list_links`: optional `status: "active" | "paused"`, passed through as the query param.
- `update_link`: optional `isActive` (alone; with any other field the tool refuses before any call,
  same rule as the engine). Same confirm rule: without `confirm: true` it only reads. The
  turn-back-on preview reads `get_link` (already on?) and then up to 5 pages of paused links
  (500) to show which destination comes back; if more than one paused row has the slug the
  engine turns on the most recently paused one. Blocked links (409 `link_blocked`) and slug
  clashes (409 `slug_in_use`) come back as the engine's message.
- No new tool (16 stay 16), no new dependency, no engine change. "Turn back on" for
  `deactivate_link` now points at `update_link` `isActive: true`.
